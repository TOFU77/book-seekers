# 技術設計

最終更新: 2026-08-01

企画内容は [concept.md](concept.md) を参照。このドキュメントは実装手段を扱う。

## 基本方針: エンジンは小さく、内容は データ

このゲームは戦闘アニメーションもリアルタイム処理もなく、**大量のテキストと構造化データを解釈して画面に出すだけ**である。技術的な難所は描画や性能ではなく、**内容が増えても壊れないこと**にある。

したがって最重要の設計判断はフレームワーク選定ではなく、**規則(engine)・素材(content)・画面(ui)の三分割**である。内容を増やすときに `content/` だけを触れば済む状態を保つ。

## スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| ビルド | **Vite** | 設定が最小。静的ファイルとして出力でき、サーバー不要 |
| 言語 | **TypeScript** | 14棚・数百冊の蔵書を扱うため、棚名の綴り間違いなどをビルド時に潰せることが決定的 |
| UI | **React** | 画面状態(棚を眺める・編成する・討論する)が多いため素のDOM操作は不利。Svelteも候補だったが、コードの大半を生成AIに書かせる前提では実績量の多いReactが安全 |
| スタイル | **プレーンCSS + カスタムプロパティ** | 「衰退した地方都市の古書店」の空気を一箇所で調律したい。フレームワークの語彙に引きずられたくない |
| 状態管理 | **React標準(useReducer + Context)** | 外部ライブラリ不要の規模。ゲーム状態は単一のツリーで足りる |
| 保存 | **localStorage + JSON書き出し/読み込み** | サーバー不要。ブラウザを消しても保存を持ち出せる |
| 乱数 | **自前の決定論的乱数(mulberry32等)** | 同じ種(seed)なら同じ町・同じ事件が再現される |

依存を意図的に少なくする。数年後に開いても動くこと、静的ファイルとして丸ごと保存できることを優先する。

## ディレクトリ構成

```
RPG0/
  docs/
    concept.md         企画
    tech-stack.md      本ドキュメント
  src/
    types.ts           共通の型定義(棚・蔵書・タグ・人物・事件)
    engine/            規則。データを解釈して動く部分
      rng.ts           決定論的乱数
      synergy.ts       シナジー判定(精読・棚またぎ・定礎)
      investigate.ts   捜査フェーズ(ペア派遣・化学反応・即席タグ)
      debate.ts        討論フェーズ(二重の壁・憑物落とし)
      layers.ts        入れ子の深掘り・意見対立
      save.ts          保存と復元
    content/           素材。ここだけ触れば内容が増える
      shelves.ts       14棚の定義
      themes.ts        主題(棚またぎの成立条件)
      books/           蔵書(棚ごとに分割)
      cast.ts          幼馴染5人(気質四軸・人物票)
      cases/           事件モジュール(動機の型・隠蔽の型・発覚の型・関係者の型)
    ui/                画面
  tools/
    validate.ts        内容検査(後述)
```

`engine/` は `content/` を知らない。規則は素材に依存しない形で書き、素材は型に従うだけにする。これにより、事件を100本足してもエンジンを触らずに済む。

## 保存の二層構造

企画で確定した「部分持ち越し」をそのままデータ構造にする。

```
TownState    周回を跨いで残る
  ├ 蔵書       店の棚にある本
  ├ 読了       誰がどの本を読んでいるか
  ├ 関係       幼馴染同士の履歴
  └ 記憶       過去の事件で何を暴き、何を収めたか

CaseState    事件ごとにリセット
  ├ 手帳       証拠・証言・道具・即席タグ
  ├ 日程       残り時間
  ├ 層         現在どの深さにいるか
  └ 壁         論理の壁・心理の壁の進捗
```

保存はこの二つのJSONを localStorage に置き、任意でファイルとして書き出せるようにする。複数の保存枠を持てるようにする(何度もやり直す前提のため)。

## 決定論的生成

事件は「動機の型 × 隠蔽の型 × 発覚の型 × 関係者の型」から組み立てるため、乱数を使う。ここで `Math.random()` を使わず**種(seed)から再現できる乱数**を用いる。

得られるもの:

- 同じ種を入れれば同じ町・同じ事件が再現できる(「この種の事件が面白かった」を共有できる)
- 不具合が再現できる
- 「やり直し」で同じ事件をもう一度違う手で解ける

## 内容検査(このプロジェクト固有の最重要ツール)

事件を組み合わせで生成する以上、**解けない事件が生成される危険**が常にある。必要なタグが今の書架では入手不可能、必要な棚を誰も読んでいない、といった事故は必ず起きる。

`tools/validate.ts` を用意し、以下を機械的に検査する。

1. **参照の健全性** — すべての蔵書が実在する棚を指しているか。事件が実在する蔵書・人物を指しているか
2. **到達可能性** — 各事件の各層について、論理の壁・心理の壁の双方に必要なタグが、その時点の書架・読了・派遣可能なペアの組み合わせで**実際に入手できるか**
3. **奥の棚の整合** — 層3が奥の棚を要求するとき、それを読める人物(柊・望月)が生存し、かつ蔵書が存在するか
4. **袋小路の検出** — プレイヤーが取り返しのつかない状態(必要な人物との関係が壊れて詰む)に入れるか

通常のゲーム開発で言うユニットテストより、**この内容検査のほうがはるかに価値が高い**。エンジンの規則は単純だが、内容の組み合わせ爆発が事故の本体だからである。

## 配布

`npm run build` で静的ファイル一式が出る。以下のいずれでも動く。

- ローカルのファイルとして開く(サーバー不要)
- GitHub Pages 等の静的ホスティングに置く
- 丸ごとZIPで保管する(長期保存)

外部APIに依存しない。ゲーム内の「検索」は、実際のWeb検索ではなくゲーム内データとして実装する(即席タグの生成)。これにより、通信なしで完結し、後年も同じ挙動で動く。

### 実際に触って分かったこと(2026-08-01)

- **単品の「かすった」(×1.7)が、急所を外した棚またぎ(×1.35)より強い。**
  実測で 単品かすり −8.5 に対し、棚またぎ主題外し −8.4。
  素直なプレイヤーへの救済として入れた値だが、組み立てる意欲を削ぐ側にも働く。
  実際に何度か遊んでから 1.5 前後へ戻すか判断する
- 捜査の記録(手応えの表明)が長い。画面では日ごとに畳んで、直近の日だけ開くべき

| `npm run typecheck` | 型検査 |

**先に事件生成の仕組みを作らない。** 手書きの1事件で討論の面白さが確認できるまで、モジュール化には進まない。面白くない討論を100本量産しても意味がないため。

## シナジーの数値(調整済み・2026-08-01)

`src/engine/synergy.ts` の `TUNING` に集約してある。バランス調整はそこだけを触る。

### 算出式

```
崩し値 = (書架の合計 × 壁の書架重み + 手帳の確度 × 壁の手帳重み)
         × 結合倍率 × 適合倍率

書架の合計 … 棚ごとにまとめ、威力の高い順に ×0.6^i(精読の逓減)
              各棚の合計を ÷(1 + 0.3 × その棚の慣れ)
```

### 壁の種類による重み

企画上の「論理の壁は証拠で、心理の壁は知識で崩す」をここで機構にしている。

| 壁 | 書架 | 手帳 |
|---|---|---|
| 論理の壁 | ×0.7 | ×2.0 |
| 心理の壁 | ×1.0 | ×1.0 |

### 結合倍率(組み合わせの筋)

| 種別 | 倍率 | 条件 |
|---|---|---|
| 単品 | 1.0 | 書架1冊 |
| 精読 | 1.2 | 全部同じ棚 |
| 寄せ集め | 1.0 | 棚は違うが**共有する主題がない** |
| 隣接(距離1) | 1.2 | 同じ区分の別の棚 + 共有主題 |
| 棚またぎ(距離2) | 1.35 | 別の区分 + 共有主題 |
| 遠望(距離3) | 1.6 | 片方が奥の棚 + 共有主題 |

### 適合倍率(相手の読み)

三段階に分ける。

| 種別 | 倍率 | 条件 |
|---|---|---|
| **筋が通った** | ×2.2 | 複数冊の**共有主題**が相手の弱点主題を含む |
| **かすった** | ×1.7 | **単品**で、その一冊の主題が弱点を含む |
| 通り一遍 | ×0.65 | かすりもせず、組み合わせも成っていない |
| 耐性棚だけで固めた | ×0.3 | 相手が既に調べている領域 |

**適合倍率(相手の読み)を結合倍率(棚の遠さ)より大きく取ってある。** 逆にすると「棚の組み合わせを解くパズル」になり、相手が誰であるかが関係なくなる — ミステリーでなくなる。実測で確認済み。

### 三つの重要な規則

**1. 「筋が通った」は複数冊の共有主題にだけ認める**

手当たり次第に3冊積んで主題を6つ乗せても、共有していなければ急所には当たらない。この規則が無いと、乱雑なプレイが半分の確率で勝ってしまう。

**2. 「かすった」は単品にだけ認める**

複数冊にも認めると、三冊撒けば主題が六つ乗って必ず当たり、**何も考えないプレイのほうが素直なプレイより強くなる**(実測で確認)。単品限定にすることで、何も考えずに強い本を出すプレイヤーにも約2割の勝ち筋を残しつつ、乱雑なプレイは1〜5%に抑えられる。

**3. 棚またぎは共有主題があるときにだけ発火する**

距離が遠いだけの寄せ集めは何も生まない。主題は10種。増やすと「どれかは必ず共有している」状態になり、棚またぎが安くなる。

### 壁の堅さと手数

| 層 | 論理 | 心理 | 手数 |
|---|---|---|---|
| 層1 | 20〜22 | 30〜32 | 8 |
| 層2 | 32〜35 | 55〜60 | 10 |
| 層3 | 55 | 100 | 12 |

手数は、組み立てるプレイヤーが5手前後で解け、何も考えないプレイヤーが8〜10手かかって
2割ほど勝つ、という釣り合いから決めている。

**両方の壁を、共通の手数の中で崩す。** どちらを先に攻めるか、手数をどう割り振るかがプレイヤーの判断になる。片方だけ崩しても決着しない。

検証結果は [playtest-01.md](playtest-01.md) を参照。

## 後でやること: 書物名をもう一枚被せる

現在は「一冊＝一つの概念」として、表題に概念名をそのまま書いている
(14棚・28冊・主題10種)。最終的には**実在の書物名をもう一枚被せたい**。

- 書物と主題の結びつきを**自明でなくする**。『逸脱の常態化』ではなく、
  実際の書名から主題を読み取らせる
- 書物名は主題数より数倍多くする。同じ主題を持つ本が何冊もある状態にする
- 読了済みの書物のうち、主題が重複しているものに**色を付けて暗示する**。
  プレイヤーは色の重なりから「この二冊は繋がる」と気づく

これは表示層と content 層の分離の問題であり、engine は触らずに済む。
